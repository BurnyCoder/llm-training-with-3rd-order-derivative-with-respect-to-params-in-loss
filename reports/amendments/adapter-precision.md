# Pre-test amendment to adapter derivative arithmetic

25 November 2026. Registered after the initial FP32 adapter pilot and before any confirmatory adapter training or test-set scoring. The original preregistration is preserved. [Original protocol](../preregistration.md) · [Raw diagnostic pilot](../../results/abstracts-pilot-s00-third-r03)

The original calibration overflowed while computing the norm of finite gradient entries. Further checks on the full pretrained checkpoint found large differences between single-precision implementations of the same penalty. Independent CPU and GPU double-precision runs on identical adapter weights, target tokens and probes agreed on the direction and scale of the fourth-order gradient. The host implementation was faster than the laptop GPU for this calculation. A separate full-weight TinyStories probe compared its original GPU calculation against double precision. [Single-precision GPU experiment](../../results/verification/pythia-joint-cuda.json) · [CPU reference](../../results/verification/pythia-fp64-cpu.json) · [GPU reference](../../results/verification/pythia-fp64-cuda.json) · [Cross-device gradient agreement](../../results/verification/pythia-fp64-agreement.json) · [TinyStories check](../../results/verification/stories-full-gradient.json)

All subsequent adapter derivative arms use a double-precision copy of the same frozen checkpoint and current QKV factors, with double-precision eager attention and the original causal mask. The two-window contraction carries its full fourth-order contribution. CUDA draws the paired random signs. The CPU computes the derivative penalty in FP64 on this machine, scales its gradient, and returns it to the ordinary GPU optimizer. Token cross-entropy, model weights, AdamW and scoring use the registered FP32 GPU path. Hessian trace and squared Hessian norm receive the same precision treatment. The combined and sign-randomized controls use these calibrated gradients. [Implementation](../../src/thirdloss/objectives.py) · [Attention backend registration](https://huggingface.co/docs/transformers/attention_interface)

The first FP32 adapter pilot remains public with its original checkpoint, scores and examples. A diagnostic phase label excludes it from development selection and inference. Recalibrate on the same training windows, rerun the entire registered grid, and identify corrected derivative runs by the `-fp64` suffix. The TinyStories protocol, seed assignments, data, update gates, strengths, token horizons and statistical decision rule retain their registered definitions. [Exclusion record](../../results/verification/numerical-exclusions.json) · [Planned runs](../planned-runs.md)

The primary computational comparison uses elapsed training time while one GPU is reserved. The raw training records separately measure the time spent in host probe calls. Subtracting these calls gives a supplementary time-accounting estimate that also excludes their transfers. It does not measure individual CUDA kernel durations. Host and dedicated-GPU memory have separate units and accounting. [Time accounting](../../src/thirdloss/train.py)

Before rerunning the adapter pilot, benchmark inference batches of 2, 8, 16 and 32 windows on 256 fixed training windows. Retain the original batch of two unless a candidate is at least 10% faster, agrees within 0.000002 nats per target and one top-one prediction with the reference, and uses at most 7 GiB of allocated CUDA memory. Select the fastest eligible batch and use it for all amended-stage development and test scoring. Training batch sizes, evaluation targets and contexts are fixed.
